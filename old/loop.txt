過去に記事でも紹介しましたが、私は自宅（私的）な環境では主にAntigravityを使っています。種々の個人的事情からGoogle AI Proをずっと契約しており、そのサービス内だからです。

その中で最近（ここ1か月くらいかな？）は、ClaudeCodeを中心に、「ループエンジニアリング」を採用している方が増えてきたなと思います。
私も使っているので、個人的な実装内容を公開します。参考になる方がいれば幸いです。

1.　背景と目的
「なんでループエンジニアリングが必要か」について簡単に触れておきます。知ってる方は読み飛ばして、次の章に行ってもいいです。

皆さんご存じのように、生成AI（LLM）はステートレスで、1度に読み込めるトークン数には限りがあります。
1つのチャットセッションで仕様策定・コーディング・デバッグを延々と続けると、Antigravity（Gemini）の広大なコンテキストウィンドウであっても試行錯誤のゴミログにより注意（Attention）が希釈され、指示の無視・既存コードの破壊（デグレ）・ハルシネーションが急増します。それを解決する手法の一つが、「ループエンジニアリング」です。

1.1　ステートレスを前提にした実行方法
指示内容をチャット会話履歴（記憶）を頼らず、仕様書・タスクリスト・Git履歴という「外部ファイル」に状態を永続化することで、トークンを効率よく使用します。

1.2　ループ・エンジニアリングの適用
「計画（Planning）」「実装（Coding）」「検品・同期（Review）」の各フェーズでセッション（Chat）を物理的に分離し、常に100%クリーンな推論能力で作業させる。つまり、ゴミプロンプトを読み直さなくていいのです。

1.3　決定論的検証（Ground Truth）の義務化
AI自身の「動くはず」という思い込みを排除し、テストスイートやビルドの終了コード（Exit Code 0）をタスク完了の絶対条件とする。

1.4　デメリット
チャットのセッションがかなり増えるので、整理が必要です。
実際の運用は、どのくらいの大きさのプロジェクトを立ち上げるかで変わると思います。その辺は、個人のカスタマイズかなと思います。

2.0　準備するもの
Antigravityは既に導入済みの前提で説明します。

2.1　グローバル設定ファイル（全プロジェクト共通）
以下の内容を、~/.gemini/GEMINI.md（Windows: C:\Users\<ユーザー名>\.gemini\GEMINI.md）として保存します。これは、Antigravityのグルーバル憲法（最高法規）です。私が使っている内容を全文公開します。

# ~/.gemini/GEMINI.md (Global Constitution)

このファイルは、AIエージェント（Antigravity / Gemini）が全プロジェクトで共通して遵守すべき「最高法規（グローバル・プロンプト）」です。エージェントはすべての行動において、以下の原則を厳格に守ってください。

---

## 1. ルールの優先順位と競合解決 (Rules & Priorities)
- **ローカルルールの遵守:** 各プロジェクトのルートディレクトリに `AGENTS.md` （またはそれに準ずる設定ファイル）が存在する場合、必ず事前に読み込み、その指示に厳密に従うこと。
- **競合時の確認義務:** この `GEMINI.md`（全体ルール）とプロジェクトごとの `AGENTS.md`（ローカルルール）の間に矛盾を発見した場合は、推測で自動解決せず、作業を一時停止して必ずユーザーに確認すること。

## 2. 言語とエンコーディング (Language & Encoding)
- **文字コードの徹底:** プロジェクト内のファイル読み書きは、特別な指定がない限り常に **UTF-8（BOMなし）** で行うこと。
- **ファイル操作ツールの優先使用:** `AICHANGELOG.md` や `Plan.md` などの作成・編集には、専用のファイル編集ツール（`write_to_file` や `replace_file_content` 等）を使用すること。
  - Windows環境でリダイレクト（`>` / `>>`）や `Out-File` によるファイル出力は、エンコーディング不一致による文字化けの原因となるため原則禁止とする。
- **日本語での記述:** ユーザーとの対話、コード内コメント、コミットメッセージ、ドキュメント類は、英語指定がない限りすべて日本語で行うこと。

## 3. 情報の鮮度と調査 (Freshness & Grounding)
- **最新情報の優先:** 技術仕様やライブラリの利用法については、Web検索を用いて最新かつ正しい情報を前提に作業・回答すること。

## 4. 標準ワークフローと自律ループ原則 (Standard Workflow)
自律タスク実行（Goal Mode / Workflows / ループ実行時）は、以下のフェーズと原則を厳守すること。

### 【自律実行の鉄則】
- **1イテレーション = 1タスク:** 1回のサイクルで複数のタスクを一気に処理しようとせず、`Plan.md` 内の最優先未完了タスク1つに集中すること。
- **客観的検証（Ground Truth）:** 実装後は必ずビルドやテストコマンドを実行し、エラーがない（Exit Code 0）ことを確認してから完了とすること。

### Phase 1: 作業開始前の準備 (Preparation)
1. **仕様書の確認:** `for_agent/` ディレクトリが存在する場合、作業開始前にすべての仕様書（`.md`）を読み込み、全体像と制約を把握すること。
2. **計画の立案:** `Plan.md` を作成または確認し、タスクをチェックボックス形式（`- [ ] タスク`）で管理すること。

### Phase 2: 作業中の原則 (Execution)
1. **計画の厳守:** 選択した未完了タスク1つを確実に実装すること。
2. **仕様書の同期（自動改訂）:** `for_agent/` 内の仕様書に変更が生じた場合は該当ファイルを改訂し、「改訂履歴」を追記すること。
3. **検証ループ:** ビルド・テスト・Linterが失敗した場合は、成功するまで修正と検証を繰り返すこと。

### Phase 3: 作業完了後の記録 (Completion)
1. **変更履歴の記録:** 作業完了後、`AICHANGELOG.md` に作業内容（Before/After、変更理由、影響範囲）を追記すること。
2. **Plan の更新:** `Plan.md` の対象タスクを `- [x]` に更新すること。
3. **Git コミット:** 変更内容をコミットすること。

## 5. 一般的な行動規範と安全性 (General AI Behavior & Safety)
- **破壊的変更前の確認:** データベース削除、`rm -rf`、インフラ破棄などの破壊的操作の前には、必ずユーザーの明示的許可を得ること。
- **簡潔なコミュニケーション:** チャットでの返答は無駄な前置きを省き、結論ファーストで簡潔に回答すること。
- **推測での作業禁止:** 曖昧な指示や環境変数の不足がある場合は、推測で動かずユーザーに確認すること。

2.2　プロジェクトごとの管理ファイル（リポジトリルート）
以下の通り、プロジェクト作成段階から配置をしておきます。私はいつも、デフォルトの形を持って置き、コピペで新規作成します。

your-project/
  ├── .agents/
  │   └── skills/           # /コマンド（Skill）として自動登録されるディレクトリ
  │       ├── plan/
  │       │   └── SKILL.md  # /plan（計画・タスク分解）
  │       ├── loop-step/
  │       │   └── SKILL.md  # /loop-step（1タスク実装・テスト・コミット）
  │       └── review/
  │           └── SKILL.md  # /review（全体検品・仕様書同期）
  ├── for_agent/            # 人間とAIが共有する仕様書（要件・API定義など）
  │   └── *.md
  ├── AGENTS.md             # プロジェクト固有ルール・検証コマンド定義
  ├── Plan.md               # タスク進捗管理（チェックリスト）
  └── AICHANGELOG.md        # AIによる変更履歴ログ

name: loop-step

# Instructions:
1. `Plan.md` を読み、最初に見つかる未完了タスク（`- [ ]`）を1つ特定する。
2. 関連する `for_agent/` の仕様を確認し、コードの実装・修正を行う。
3. `AGENTS.md` に記載された検証コマンドを実行し、エラーがない（Exit Code 0）ことを確認する。
   - 失敗した場合はエラーログを修正し、パスするまで繰り返すこと。

5. `Plan.md` の該当タスクを `- [x]` に更新する。
6. Git コミットを作成する（例: `git commit -m "feat: ..."`）。
7. すべてのタスクが `- [x]` になった場合は「全タスク完了」と報告せよ。

3.　日常の開発フロー（実践サイクル）
イメージとしては、下図の感じです。

画像
フロー図
新機能開発やプロジェクト立ち上げ時は、以下の3フェーズで進めます。
*セッション破棄は、削除するのではなく、もう使わないという意味です。

【Phase 1: Planning（計画）】
1. New Chat を開く。
2. AIと壁打ちして `for_agent/*.md`（仕様書）を作成。
3. チャット欄で `/plan` を実行 ──> `Plan.md` が生成される。

　 (セッション破棄 ──> New Chat)

【Phase 2: Coding Loop（実装ループ）】
1. New Chat を開く。
2. チャット欄で `/loop-step` を実行。
(未完了タスクを1つ実装 ──> テスト ──> コミット ──> 終了)
3. `Plan.md` に未完了タスクが残っていれば、1〜2 を繰り返す。

(セッション破棄 ──> New Chat)

【Phase 3: Review & Sync（検品・同期）】
1. New Chat を開く。
2. チャット欄で `/review` を実行。
(第三者視点でコード点検 ──> `for_agent/` 仕様書を同期)
3. 人間が実環境で最終確認する。

4.　どう動いているか
AIとの会話履歴は、回数を重ねるほど「過去の試行錯誤やエラーログ」というノイズで埋め尽くされます。 本手法では、重要な文脈（Context）をすべて以下の外部ファイルに永続化しています。

プロジェクト仕様: for_agent/*.md

実行ルールと検証方法: AGENTS.md

全体の進捗状況: Plan.md

コードの確定状態: Git コミット履歴

そのため、セッションを毎回「New Chat」で破棄しても、AIは必要なファイルだけを読み込んで、直前の作業の続きから100%の知能で再開できます。

4.1　ループ実行の内部メカニズム（Ground Truth 検証）
/loop-step を実行した際、Antigravity の内部では以下の自己完結ループが回ります。

画像
ループのイメージ
AIは「書いたから動くはず」という自己評価を許されず、実際のテストやコンパイルが成功するまでプロンプト内で修正を繰り返します。これにより、人間が手元で動かす前に基本的なバグが自動排除されます。

5. さいごに（運用のコツとトラブルシュート）
以上が、直近で私が使っているAntigravityのループエンジニアリングです。
ほぼそのままコピペで、誰でも使えるようになると思います。
最後に、おまけとして運用のコツとか書いておきます。

① 1タスクの粒度は「小さく」保つ
/plan で生成された Plan.md の1項目が大きすぎる場合（例:「ユーザー認証機能の全実装」）、AIが1回の /loop-step で息切れします。「DBスキーマ作成」「APIエンドポイント実装」「バリデーション追加」のように、1回のテストで検証できる単位に分解してください。

② 実環境で想定外のエラーが出た場合
人間が動かしてエラーが出た場合、過去のセッションを再利用してはいけません。 「New Chat」を開き、エラーログを貼り付けて以下のように指示してください。

「実環境で上記のエラーが発生しました。AGENTS.md と該当コードを確認し、
原因の特定と修正を行ってテストを通してください。」 

copy
これにより、最短手数で安全にバグが修正されます。

③ 仕様書の形骸化を防ぐ
開発が進むとコードと仕様書が乖離しがちですが、本手法では /review ワークフローが仕様書（for_agent/）を最新コードに合わせて自動改訂します。リポジトリ内の仕様書が常に「正本」として維持されるため、将来の機能追加時もセッションC、セッションDと迷わず開発を継続できます。
